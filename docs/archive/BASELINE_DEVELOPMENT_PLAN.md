# KernelAgent 参考基线与单智能体对照计划

这份计划采用资格检查前拟定的题单和预算。后续实测结果与正式题单见[基线资格记录](../AGENT_BASELINE_PLAN.md)。

## 一、修正计时，重放已有内核

当前评测先把候选和搜索中保留的最快内核配对计时，再把候选和 PyTorch 库配对计时。第二轮丢掉了候选的样本，报告把第二轮库的中位延迟除以第一轮候选的中位延迟。先写一个失败的回归测试，给同一候选在两轮配对中设定不同延迟，再修改评测与汇总逻辑。修复后，每个速度比都必须能从同一轮的两组原始样本算出。新协议单独版本化，历史报告按当时的口径解释。[计时实现](../../kernel_study/judge/timing.py) · [已归档的归约实验](REPAIR_ROUND.md)

第一项 GPU 实验只用已有源码，模型调用为零。这两个旧任务的延迟主要是每次 launch 约 17 μs 的固定开销（归档数据中 1、2、3 次 launch 的中位延迟约为 19、34–36、49 μs），重放得到的加速比按 launch 次数的变化来解释。

1. 重放 `softmax_irregular` 和 `layernorm_irregular`，两者均为 FP32、形状 `513 × 781`。将项目起点、归档的最终候选、PyTorch eager、固定模式的 `torch.compile` 和 TritonBench 的手写实现放在同一张表里。所有实现都测预热后的完整前向调用，使用相同的输出分配口径。报告中位延迟（μs）、四分位区间和配对加速比，编译耗时单记。
2. 用同一内核对自己做重复测量。上轮 16 份基线自比中有 2 份被判为确认加速。先用自比数据校准胜负线，再换一份独立作业验收。建议每个算子做 20 次自比，至多误判 1 次，同时能重复测出已知双次启动实现与融合实现之间的延迟差。验收同时检查误报和辨别真实差异的能力。这里定出的胜负线只适用于几十微秒量级的旧任务，第二节的公共题在预检时重新做自比校准。
3. 给两轮归约实验中所有 LayerNorm 最终候选及其起点补测大偏置、小方差和近常量输入，沿用原容差。用 FP64 先求均值、再求中心化平方和，核对 PyTorch 参考与候选各自的误差。`layernorm_irregular_single_22` 的第 8 个候选使用 `E[x²] − E[x]²`，而其双块展开循环在 `N=781`、`BLOCK=1024` 时执行 0 次。压力输入可以检验实际执行的方差公式。旧终验和新压力测试分别记录。

历史数据可在 `results` 分支的 `reports/REPAIR_ROUND_REPORT.md`、`reports/repair_round_comparison/runs.csv` 和 `results/repair-strong-3584057/campaign/` 下核对。

## 二、接入公共任务，跑通参考 agent

**设备。** 开发对照使用 Lonestar6 的 A100 PCIe 40GB。驱动为 570.195.03，Torch 为 2.12.1+cu126，Triton 为 3.7.1。六道题均在公开形状上完成了三次起点正确性检查。同一题和种子的两次搜索及终选配对在同一张卡上进行，记录该卡的 UUID。作业先将 Python 环境、上游包和已登记提交放到节点本地盘。启动前用上游的 30 秒校验器验证起点，通过且用时不超过 25 秒才开始搜索；只有慢校验或超时允许在同一分配上重试，最多三次。A800 的测量只用于开发记录。

对每道 KernelBench 题，固定题目、输入形状、dtype、数值容差、验证种子和起始内核。优先使用已经公开且通过本地终验的优化前源码。上游示例目前只确认 matvec 有现成起点，其余题的起点来源在题单冻结时一并登记，并记录它相对 PyTorch eager 和 `torch.compile` 的延迟，使每题的可优化空间在 agent 运行前已知。两方取得同一份带 `kernel_function` 的完整起点、题目文件和校验脚本，最终候选交给同一个评测器，用搜索期间未见的输入检验。TritonBench 提供适用算子的性能参照。

KernelAgent 直接运行上游 `greedy`。本仓库只适配它的任务输入、候选输出和运行记录。本地 `single` 每个候选依次调用分析、建议、实现、复盘。分析根据测量解释瓶颈，建议至多三句，实现交付 `source` 和 `rationale`，复盘交付 `diagnosis`、`outcome` 和 `next_step`。只有实现阶段提交源码。正式比较中的 `multi` 沿用同一流程与字段。两边提交同一种 native 模块，包装函数读取输入形状和步长、分配输出与所需暂存区、启动 Triton 内核并返回结果。两个 agent 的候选在执行前经过相同的静态检查。仅修改分块或 launch 参数也可参加评测。与起点语句相同的提案消耗候选名额。报告按 agent 单列静态检查、编译、数值和未确认提速的次数。[本地搜索循环](../../kernel_study/agents/local.py) · [候选模块检查](../../kernel_study/judge/policy.py)

首次运行用上游自带的 matvec。其起始内核要求 BF16，`greedy` 示例使用 1 个 worker，示例机器配置为 H100 NVL。固定上游提交，在目标 GPU 上依次验证起点、Nsight Compute 能取到的计数器、一次真实模型提案，以及该提案在公共评测器上的独立复测。核对实际模型调用、token 和费用。冒烟结果单列。

**参考 agent 校准。** 上游公开的 matvec 结果在 H100 上用 opus-4.5、4 个 worker、8 轮得到：起点 9.52 ms，直接让模型迭代 8 轮为 3.20 ms，KernelAgent 为 1.95 ms，`torch.compile` 为 2.09 ms。本计划给 `greedy` 的预算远小于这一配置。A100 空闲对照、独立自比和归档终选复测完成后，在 matvec 上用单 worker 跑满 8 轮做一次校准，记录每轮最好延迟，并与同机实测的起点和 `torch.compile` 对照。校准只回答上游流程在本机和所选模型下能否把起点推到接近 `torch.compile`。做不到时先查环境、模型和 Nsight Compute 反馈，再进入对照。校准费用单列，不计入对照矩阵。可实现的延迟以 `torch.compile` 和手写实现为锚，`greedy` 在小预算下的成绩只代表该预算下的参考水平。

进入对照前，冻结 KernelBench、KernelAgent 和本仓库的提交，GPU 型号与驱动、Torch/Triton/CUDA 版本、双方共同支持的模型快照与推理设置，以及每道题的起点和预算。公开题先按原始形状做零推理预检，实测正确性、峰值显存和计时波动。显存或精度不满足的题显式记录，在看到 agent 成绩前确定最终题单。

## 三、先测当前 single，再按差距决定改什么

| 实验 | 任务和重复 | 搜索次数 | 候选数上限 |
| --- | --- | ---: | ---: |
| 开发对照 | KernelBench Level 1 的 matvec（4）、softmax（23）和 LayerNorm（40），每题每个 agent 独立搜索 2 次 | 12 | 48 |
| 针对性复验 | 仅在开发题上复验一个能解释已观测差距的改动 | 按差距决定 | 单列预算 |
| 冻结验收 | 建议留出标准矩阵乘（2）、GELU（26）和 RMSNorm（36），每题每个 agent 独立搜索 3 次 | 18 | 72 |

开发对照比较当前 `single` 和 KernelAgent `greedy`。冻结验收比较开发结束时选定的本地版本和同一个 `greedy`。两张完整矩阵合计 30 次搜索、最多 120 个候选，冒烟、校准和针对性复验另计。留出题的 agent 成绩只在策略冻结后打开。

softmax 和 LayerNorm 是本地共享指引针对调过的算子，matvec 是上游自带示例，这三题只用于开发。留出题取双方都没有专门调过的算子。上游公开评测覆盖过 Level 1 的全部题目，本仓库早期试验跑过另一种形状的矩阵乘，这两点在报告中注明。

**预算与代码改动。** 每次搜索建议上限为 4 个候选、16 次实际模型调用。提交后被规则拒绝、编译失败或数值错误都消耗候选预算，下一次修复另计。KernelAgent 的一个 round 可能调用模型多次，因此在调用发生处记账。新接口的 matvec 冒烟只运行 `single`，最多 1 个候选、4 次模型调用。已归档的首对费用为 0.085804 美元，新台账从余额 11.5019564 美元开始。[Campaign 入口](../../kernel_study/campaign/jobs.py) · [预算实现](../../kernel_study/budget.py) · [模型调用记账](../../kernel_study/providers.py)

**比较口径。** 按题目和独立重复编号配对，先列出多少次搜索产出了通过终验的新候选，再列出最终内核延迟（ms）、相对共同起点和 `torch.compile` 的加速比、调用数、token、估算美元费用和 GPU 时间。退回起点的搜索留在分母中，实际测量其最终延迟，并标记为回退。分别报告相同候选数和相同累计花费下已找到的最好正确内核。预算中断的搜索保留已完成记录，注明可比较到哪个预算位置。

两个 agent 搜索结束后，同一个裁判按提案顺序核对新候选。候选通过未见种子和压力输入验证，且与当前终选的两轮配对都快过本题阈值，才取代当前终选。最后再与共同起点复核。未选中任何候选时，起点代表这次搜索。上游 greedy 自选的源码和延迟另存。两个 agent 都完成后，在同一进程对两个终选做 AB/BA 计时。每个种子的验收比值取自这一次配对的两组样本。若此步中断，可在原设备用 `kernel-study report 阶段 输出目录 --measure-pairs` 补测，消耗模型调用为零。

正式搜索前，对每道题的共同 native 起点运行 `kernel-study preflight stress --case 题号 --output 预检目录`。终验包括零值、常量、大数和负数输入，LayerNorm 另测大偏置。逐元素对照 FP64，允许误差取本题的绝对和相对容差，加上 eager 在该元素上的实测误差。每次调用由候选分配输出，裁判核对整个输出，并在执行前后逐个核对输入。

仅在请求遇到传输中断时，同一作业允许用 `--retry-transport` 从起点重跑一次。原搜索、重跑和未确认结算的费用都保留。每个题目和种子只计一个终选，报告另列两次运行的调用和费用。预算耗尽或模型服务拒绝请求时，该作业结束。设备峰值、各阶段轮数、候选和调用上限随实验配置冻结，修改报告排版可沿用已冻结的搜索与评测代码。

**针对性复验。** 每次只改一个因素，并在同一批开发题上与改动前的版本配对。

| 观察到的差距 | 下一次只改什么 | 用什么判断 |
| --- | --- | --- |
| 双方能写出正确内核，KernelAgent 的延迟持续更低 | 给本地 `single` 相同的 Nsight Compute 反馈，保留四次调用流程 | 比较每题最终延迟和相对起点的改进，观察差距缩小多少 |
| 最终延迟接近，本地调用更多或花费更高 | 在同样反馈下改为每轮一次调用，直接提交下一稿 | 比较达到同一延迟所需的调用和费用，同时检查正确率 |
| 失败集中在启动接口，参考 agent 可运行同类优化 | 对齐双方允许修改的设备代码和 launch 范围 | 重放原被拒的候选，再比较通过终验的候选数与延迟 |

当前版本在开发对照中已达到目标时，直接进入冻结验收。若双方几乎都退回起点，先用已知正确实现测量该题还有多少加速空间，再判断是否需要调整搜索预算。

## 四、冻结参考基线

建议在打开留出结果前登记两项工程标准。在共同预算下，本地版本产出通过独立终验的新候选的搜索次数至少与 `greedy` 持平。其次，以每个配对中“本地最终延迟 / greedy 最终延迟”为比值，先在每题内对重复搜索取几何平均，再在三道留出题间等权取几何平均，结果应不超过 **1.10**。10% 是本次选基线的实用容忍度。报告逐题列出结果，接近边界时用独立作业复测。适用范围限于冻结的设备、任务和预算。

上一轮的最终加速比呈双峰分布：成功的搜索集中在 1.77–1.98×，其余退回起点。若新题上也是如此，某题三次搜索中一方多回退一次，就会使该题比值偏离约 2^(1/3) ≈ 1.26。因此比值越线而双方回退次数只差一次时记为待定，搜索间差异和计时噪声分开报告。

| 验收结果 | 后续采用的基线 |
| --- | --- |
| 当前 `single` 达标 | 冻结当前版本作本地基线，保留 KernelAgent greedy 作外部参照 |
| 只有改进版达标 | 冻结改进版，同时保留能解释改进来源的配对记录 |
| 本地版本持续落后 | 采用 KernelAgent greedy 作为主要能力基线，本地 `single` 用于后续角色消融 |
| 矩阵因预算中断、独立复测跨越判定边界，或双方几乎都退回起点 | 将本地基线资格记为待定，并列出还缺哪些观测 |

历史台账按归档用量估算，25 美元上限尚余 **11.59 美元**。旧 GPT-4.1 `single` 的四次归约搜索，前四个候选各花 **0.224–0.269 美元**。KernelAgent 在新题上的费用需实测。第一笔推理预算用于上游冒烟和首个完整配对，再用实际 token、价格和 GPU 时间估算剩余矩阵。预算以同一本台账累计。[历史预算和实验规模](NEXT_EXPERIMENT_PLAN.md)

交付物包括冻结的任务清单、源码和配置，独立复测命令，完整的候选、失败和原始计时，以及按题配对的验收表。代码改动按失败测试、实现、测试通过的顺序进行。这条工作线的本地测试和 GPU 作业统一写进仓库根目录的一份实验日志，每次记录动机、对应改动、精确命令、结果及据此能得出的结论。第一项实现工作是配对计时的回归测试与修复，随后运行零推理重放。
